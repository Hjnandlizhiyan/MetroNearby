# 班次表管理

落地日期：2026-09-19。

本功能管理的是某交路每天发出的**班次数和逐班起点时刻**，不是线路投入的实体列车组数量。同一组实体列车一天可能往返多次，离线数据无法可靠恢复车辆编号或周转关系。

## 管理维度

设置页进入“班次表管理”后，依次选择：

1. 线路；
2. 交路，包括全程车、内置区间车和用户添加的区间车；
3. 工作日或周末。

三个维度分别保存，修改一条线路的工作日全程车不会影响其周末班次、反向交路或其它线路。原本没有某日型服务的区间车，也可以逐班添加该日型的班次。

## 编辑方式

- 页面显示系统班次数、当前班次数以及是否已手动覆盖；
- 每一班显示最终时刻、同序号系统时刻和提前/延后量；
- 可以逐班添加、修改、删除；
- 可以输入新的总班次数自动生成预览；
- 总数生成保留当前首末班，并按原序列做分位插值，尽量保持高峰密、平峰疏的相对分布；
- “恢复当前交路”只清除当前交路、当前日型的手动表。
- “恢复整条线路全部默认班次”会清除所选线路所有交路和日型的手动表；到站校准、区间车和其它线路不受影响。

## 同一班车的中间站修正

每一趟班次都有稳定 `id`。打开“沿途站”后，可修改该班车经过的起点、中间站或终点：

- 修改起点会整体平移该班车及其已有中间站锚点，班次 `id` 不变；
- 修改中间站会从本站开始形成新锚点，相同延误量自动传播到后续站；
- 后续再修改另一站时，以新站为下一个锚点，从该处重新确定延误；
- 区间车只列出自身起终点之间的站；反向交路和环线按实际运行方向排列；
- 改变总班次数会重新建立班次编号并清除中间站修正，避免旧锚点错配到另一趟车。

保存前执行两级校验：同一班车的后站必须晚于前站；同一交路内，后一班车在任何共同站点都必须晚于前一班车。时间倒置、追平和超车都会被拒绝，并在编辑弹窗显示具体车站与冲突班次。

总班次数自动生成只是帮助用户整理完整时刻表，不代表运营方真实排班。保存前应检查逐班预览。

## 数据与预测优先级

兼容起点逐班表仍保存在 `UserOverrides.serviceDepartures`：

```text
patternId -> serviceType -> 起点站逐班时刻
```

带中间站修正的新版数据保存在 `UserOverrides.serviceTrips`：

```text
patternId -> serviceType -> [班次 id、起点时刻、站点锚点]
```

预测时按交路起点时刻叠加站间运行偏移，得到沿线各站到站时刻。优先级为：

1. 带稳定班次编号与中间站锚点的 `serviceTrips`；
2. 兼容起点逐班表 `serviceDepartures`；
3. 用户原有的站点级 `exactDepartures`；
4. 内置站点级 `exactDepartures`；
5. 首末班与发车间隔推算。

手动班次表与到站锚点解决的问题不同：班次表是长期重复的工作日/周末基线；两小时锚点和间隔学习仍用于当天临时提前、延误或间隔变化。

## 验证

纯逻辑测试覆盖工作日/周末隔离、起点到中间站传播、多个站点锚点、稳定班次编号、站序倒置、防追平与防超车、正反方向、北京环线双方向、区间车范围、跨线路持久化、恢复单一日型、总班次数重排、分钟容量校验和逐班输入规范化。当前全量 382 个单元测试通过。
